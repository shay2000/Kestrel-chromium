# Chromium crash investigation and ordinary user edge cases

Implementation and updated Mac results are recorded in [the lifecycle fix follow-up](CHROMIUM_LIFECYCLE_FIXES_2026-10-31.md). The review below preserves the original source findings and hypotheses; its initial failing restart result has since been superseded by a passing native store/restart run.

Reviewed 31 October 2026 against Kestrel `9a455954162eeba705a3f72d3fa6b49cf22e5f4a`, pinned CefSwift `b18cceef8afaf6686147e19a9239f31c2dd81541`, and the matching CEF source `4fa4ab516dacf6c49fc7e6e70d2b7ebce29fa35f` (CEF 156.0.14 / Chromium 156.0.8078.48).

The strongest explanation for the observed crash is incomplete native browser tracking followed by premature CEF shutdown. There are concrete defects in browser identity, shutdown admission and cancellation handling. The exact object that faults inside CEF has not been identified. This is an investigation and implementation map; the proposed fixes below are not implemented or accepted.

## What the runner actually established

Both real store installations succeeded in [run 41191810296](https://github.com/shay2000/Kestrel-chromium/actions/runs/41191810296). Google Translate and Dark Reader displayed native permission prompts, and Dark Reader modified example.com. Quitting then crashed the original process in CEF shutdown. After relaunch, both package directories existed but Dark Reader did not inject its page styles.

[Run 41192769207](https://github.com/shay2000/Kestrel-chromium/actions/runs/41192769207) tested a main-queue termination deferral. It reproduced the problem:

| Time, UTC | Observation |
| --- | --- |
| 10:30:58 | Google Translate package installed |
| 10:31:23 | Dark Reader package installed |
| 10:31:26 | Dark Reader: ten styles, metadata marker, background `rgb(24, 26, 27)` |
| 10:31:29 | Relaunched Kestrel, PID 10181 |
| 10:31:30 | Both installed manifests found after relaunch |
| 10:32:05 | Acceptance failed: Dark Reader did not inject after restart; crash report collected for original PID 5680 |

The original process faulted on `CrBrowserMain` with `EXC_BAD_ACCESS` / `SIGSEGV`, accessing a repeated `0xef` address. That is consistent with an invalid lifetime or freed-memory access, but does not identify which object or component made the mistake. The symbolicated Swift frames show `CefRuntime.shutdown()` reached through `handleTerminationRequest()` and the queued termination closure. The CEF frames show nearest exported symbols, not a fully symbolicated internal CEF stack; names such as `v8_internal_simulator_ProbeMemory` do not establish a V8 defect.

The deferral experiment was removed after it failed. It shows that moving the termination request onto the main queue alone is insufficient. The original synchronous shutdown inside `OnBeforeClose` remains a separate defect in the pinned upstream implementation. [Screenshots, events and full crash reports](https://github.com/shay2000/Kestrel-chromium/actions/runs/41192769207/artifacts/13039762082) are retained until 30 November 2026. See also [the store acceptance record](CHROME_WEB_STORE_ACCEPTANCE_2026-10-31.md).

## Prioritised cause and solution map

“Source-confirmed” means the implementation has the stated gap. It does not mean that gap has been isolated as the cause of the recorded crash. Only the store-install/quit/relaunch sequence above has reproduced that crash so far.

| Priority / ID | Ordinary user action | Finding and confidence | Proposed solution |
| --- | --- | --- | --- |
| P0 / C1 | Install an extension, leave its welcome/options window open, then quit; or quit with Inspect/DevTools open | **Leading crash hypothesis; source-confirmed tracking gap.** Chrome-created browsers can have no client, no lifecycle callbacks and no entry in CefSwift's browser registry. Shutdown treats that registry as complete. The exact native window responsible in the recorded run is not known. | Supply CEF's default client; register every actual browser ID, including native auxiliary browsers. Close and drain all of them before shutdown. |
| P0 / C2 | Close a native popup while its original page remains open, or quit with both open | **Source-confirmed identity bug.** A shared client's close callback ignores the callback browser's ID and closes its original wrapper. Native popup views deliberately have no wrapper. This can remove the wrong registry entry and make shutdown see an incomplete count. | Route lifecycle and other events by the actual callback browser ID, or give each allowed popup its own client and wrapper. Make duplicate close notifications harmless. |
| P1 / C3 | Open a tab/link and immediately press Cmd+Q; open a link while quit is pending | **Source-confirmed admission gap; crash scenario untested.** Chrome browser creation is asynchronous. Pending creation is absent from the runtime registry, and no quitting-state gate prevents new work from creating a browser. | Track pending creations and creation failures. Stop admitting new tabs/popups while quit is pending; cancel queued app creation tasks and close late arrivals. |
| P1 / C4 | Close an unsaved form tab, then choose **Stay** | **Source-confirmed close/cancellation mismatch; native reproduction pending.** Kestrel removes the tab's stores and delegate immediately after requesting a cancellable close. A browser that stays open can lose its tab UI and owner callbacks. | Keep tab identity, model and delegate until close is confirmed. On cancellation, retain the visible tab and form. Use a closing record tied to the exact browser generation. |
| P1 / C5 | Press Cmd+Q, choose **Stay**, continue browsing, then close the last page | **Source-confirmed sticky quit state; native reproduction pending.** `isTerminationRequested` is set to true but has no cancellation reset. A later last-browser close can re-enter app termination even though the user cancelled quitting. | Model quit as a cancellable operation with an identity. A cancelled unload restores running state; later callbacks from the old quit cannot complete a new one. |
| P1 / C6 | Quit or close a window while a site permission or JavaScript dialogue is open | **Source-confirmed nested modal execution; shutdown interaction untested.** Permission and JS handlers enter `NSAlert.runModal()` from CEF callbacks. A main-queue hop does not guarantee that all CEF callback stacks have unwound when nested event loops are involved. | Prefer asynchronous sheets and CEF's retained callback mechanisms where available. Track active callbacks/message-pump work; never tear CEF down while they are active. Respect dialogue cancellation. |
| P2 / C7 | Repeatedly close/reopen tabs or pinned pages during a long session | **Source-confirmed cleanup gap on asynchronous close paths; growth unmeasured.** The model/browser registry retains browsers strongly and is keyed by `ObjectIdentifier`. Its detach happens through a weak delegate that Kestrel may discard before close completes. Stale entries can accumulate, and model identities can later be reused. | Explicitly release mappings when retiring a model, retain close ownership separately, and use stable identity plus generation checks so an old callback cannot detach a replacement browser. |
| P1 / C8 | Restart just after installation or reopen after an unexpected quit | **Runtime-confirmed missing activation; cause unresolved.** Package files survive but live extension operation does not. Unflushed profile state, disabled registration and a startup loading failure remain separate possibilities. | First obtain a clean profile teardown. Then compare Chromium's actual installed/enabled state and extension startup diagnostics before/after restart, and verify a real page effect. |

## Why C1 and C2 come first

[CefAppHandlers.swift](https://github.com/Rajaniraiyn/CefSwift/blob/b18cceef8afaf6686147e19a9239f31c2dd81541/Sources/CefKit/CefAppHandlers.swift#L31) fills context-initialisation, message-pump and child-launch callbacks, but never sets `get_default_client`. The structs are zero-initialised. The pinned [CEF API contract](https://github.com/Rajaniraiyn/CefSwift/blob/b18cceef8afaf6686147e19a9239f31c2dd81541/Sources/CCef/include/include/cef_browser_process_handler.h#L141) explicitly says that a null default client leaves a Chrome-UI-created browser unmanaged, without callbacks, and blocks application shutdown until its window is closed manually. Matching [CEF implementation](https://github.com/chromiumembedded/cef/blob/4fa4ab516dacf6c49fc7e6e70d2b7ebce29fa35f/libcef/browser/chrome/chrome_browser_delegate.cc#L522) falls back to that hook when no client was supplied.

This is directly reachable through a normal Inspect action: [CefBrowser.showDevTools](https://github.com/Rajaniraiyn/CefSwift/blob/b18cceef8afaf6686147e19a9239f31c2dd81541/Sources/CefKit/CefBrowser.swift#L128) passes a null client. Matching CEF source routes that explicit null through the default-client fallback. Native extension-created pages/windows also need lifecycle coverage, but the existing runner events do not identify which creation path their windows used.

For shared-client popups, the [CEF popup contract](https://github.com/Rajaniraiyn/CefSwift/blob/b18cceef8afaf6686147e19a9239f31c2dd81541/Sources/CCef/include/include/cef_life_span_handler.h#L56) says the client defaults to the opener's client. [BrowserClient.on_before_close](https://github.com/Rajaniraiyn/CefSwift/blob/b18cceef8afaf6686147e19a9239f31c2dd81541/Sources/CefKit/BrowserClient.swift#L104) releases the callback browser argument and then calls `client.browser?.handleBeforeClose()` without comparing IDs. [CefChromeBrowser's popup delegate](https://github.com/Rajaniraiyn/CefSwift/blob/b18cceef8afaf6686147e19a9239f31c2dd81541/Sources/CefKit/CefChromeBrowser.swift#L317) explicitly drops popup browser references because those views have no wrapper. This is more than a missing delay: it is incomplete ownership and event routing. Title/loading events also use the client's original browser, so auditing only the close callback is insufficient.

Kestrel normally turns ordinary HTTP(S) `window.open` requests into its own tabs through `ChromiumTabStore.webView(for:)`. Those requests do not automatically take the native popup path. Reproduction should target the native Chrome/extension/DevTools paths rather than claim that every website popup is affected.

[CefRuntime.unregisterBrowser/handleTerminationRequest](https://github.com/Rajaniraiyn/CefSwift/blob/b18cceef8afaf6686147e19a9239f31c2dd81541/Sources/CefKit/CefRuntime.swift#L401) shuts down as soon as its wrapper registry is empty. Matching [CEF teardown](https://github.com/chromiumembedded/cef/blob/4fa4ab516dacf6c49fc7e6e70d2b7ebce29fa35f/libcef/browser/browser_host_base.cc#L295) still has observer and WebContents cleanup after `OnBeforeClose`. Re-entering global shutdown during that callback is unsafe. Deferring helps that ordering, but does not add the missing browsers or correct a misrouted close callback. CEF also [destroys remaining browsers during global shutdown](https://github.com/chromiumembedded/cef/blob/4fa4ab516dacf6c49fc7e6e70d2b7ebce29fa35f/libcef/browser/context.cc#L558), so a wrapper count of zero is not proof that native teardown is complete.

## Application-level locations for the remaining cases

- **C3:** `ChromiumTabStore.swift:649` queues new-tab creation from popup callbacks; `chromeBrowser(for:)` at line 671 has no quitting gate. CefSwift's `CefChromeBrowser.create` documents asynchronous browser creation, while runtime registration occurs later in `CefBrowser.adoptRaw`. A pending browser can therefore exist before the registry contains it.
- **C4/C7:** `ChromiumTabStore.swift:207` requests `chrome.close()` and then clears stores, models and delegates at lines 217–220. `closeTab` removes the tab immediately. CefSwift documents that this close can be cancelled by `beforeunload`. `CefBrowserRegistry.swift:12` keeps strong entries; `CefBrowserDelegateProxy.swift:65` performs detach only if its weak model still exists and the delegate receives the callback.
- **C5:** the pinned runtime has one `isTerminationRequested = false` initialiser and a true assignment on quit, with no unload-cancellation transition back to false. The default JS presenter has an actual **Stay** result, so cancellation is reachable.
- **C6:** `CefBrowserDelegateProxy.swift:115` uses `runModal` for permissions. CefSwift's `CefJSDialog.swift:103` and line 116 do the same for JavaScript and unload dialogues. Its pump has an `isPerformingWork` guard around message-loop work, but shutdown does not consult that guard.
- **C8:** the acceptance harness's manifest check establishes package survival only. Its failed post-restart Dark Reader style check establishes missing operation on that page. Neither tells us Chromium's enable/disable reason or whether extension startup completed.

## Implementation order and guard conditions

1. **Make native lifecycle observable first.** Log browser IDs, parent/client association, creation start/completion/failure, close requests, `OnBeforeClose`, browser-view destruction, window destruction and runtime counts. Log default-client requests and any callback ID mismatch. This requires bounded runner diagnostics in the pinned glue; URLs, page content and profile secrets are unnecessary. Preserve the existing failing acceptance as the baseline.
2. **Complete ownership and identity.** Implement the default client and register auxiliary browsers; repair shared-client routing, either by assigning separate popup clients or looking up the callback's actual ID. Ensure every admitted browser has exactly one terminal transition and each retained CEF reference has a balanced release. An ID check that merely ignores an untracked popup's close does not solve its missing ownership.
3. **Centralise quit.** Use explicit running, closing, finalising and stopped states. Closing blocks new admission, waits for pending creation and all admitted browsers, and honours unload cancellation. Keep the message pump working while browsers close. Finalising is entered once, outside active CEF callbacks/pump work, only after browser/Views references needed by the host are released. Follow the external-message-pump contract rather than transplanting the sample's internal-loop API calls into SwiftUI. A timeout records a hang; it must not silently force-close unsaved forms or make the test pass.
4. **Make tab close transactional.** Keep the tab and delegate until the browser accepts and completes close. Cancel returns the same visible tab, form and selection. Finish cleanup with stable identity/generation guards, including split panes and pinned pages. Closing the last tab without a pending quit should leave Kestrel usable.
5. **Resolve restart activation separately.** On the disposable profile, inspect only the two test extensions' registered/enabled state, disable reasons and worker errors. Compare immediate restart with a settled installation, and retain the live page check. If a clean quit still loses activation, debug extension startup as an independent fault. `FlushCookieStore` is not a flush for extension preferences; profile deletion or re-importing at every startup would hide the defect.

If native lifecycle counts are complete and teardown still faults, symbolicate the CEF frames using debug symbols matching the framework UUID from the exact failing app. Then isolate the implicated CEF/Views/profile code and compare a minimal Chrome-style CEF application on the same pinned engine. An engine revision change is a controlled follow-up experiment after that evidence, not an established fix.

## Focused Mac reproduction and acceptance matrix

Use a disposable profile for each independent comparison, with its path explicitly set by a runner-only harness. Record the effective profile path across relaunches. Keep the distribution app's defaults and existing user data untouched. The existing native-store run loads an unpacked MV3 fixture too, so include both a no-fixture baseline and the existing fixture-plus-store case.

| Case | User sequence | Required observation |
| --- | --- | --- |
| Baseline | Open a normal page, quit and relaunch with no extensions; repeat with only the fixture | No crash, orderly counts, usable relaunched page |
| Extension windows | Install Translate alone, Dark Reader alone, then both; quit once with welcome/options windows open and once after manually closing them | Which native IDs and windows exist at quit; all closed before finalisation; live extension effect after relaunch |
| Inspect | Open Inspect/DevTools, close it and continue using the page; separately quit while it is open | Default-client request and auxiliary ID captured; parent browser remains attached after DevTools closes; clean quit |
| Rapid close | Open a normal HTTP(S) background tab and immediately close it or quit; repeat for a native auxiliary window | Pending creations drain; late callbacks do not create a page after finalisation or attach to a closed/reused tab |
| Unsaved form | Use an interactive local `beforeunload` fixture; close tab → Stay; quit → Stay; then continue browsing and close the last page | Same form and tab remain after Stay; cancelled quit cannot later terminate the app |
| Last tab / pinned / split | Close the last page; reopen a pinned page immediately; close one split pane while the other loads | App stays usable, surviving page stays attached, old callbacks do not detach a replacement |
| Dialogue | Open a JS alert or permission request, cancel/answer it, then close/quit; attempt Dock Quit while the dialogue is active where macOS allows it | No finalisation during an active CEF callback, no double completion, usable cancellation path |
| Installation timing | Restart after confirmed installation, then repeat after installation has settled; also reopen following a captured unexpected quit | Correct Chromium registration and enablement, worker diagnostics and live page operation; surviving files alone never pass |
| Long session | Repeat ordinary open/close/reopen actions, including background tabs and pinned pages | Registry/live-instance counts return to their expected baseline; memory trend is measured rather than inferred from source |

For every crash, capture process identity, matching app/framework UUIDs, `.ips`, lifecycle events and final counts. A fix is accepted only when the original two-extension case and the relevant neighbouring cases pass in the actual packaged Mac app. This review added no runtime changes and performed no new Mac execution; the runtime evidence cited above is from the two prior runner runs. Linux or source-only checks cannot validate these lifecycle fixes.
