# Native extension actions in Kestrel

[Kestrel Chromium 1.0.2 is published](https://github.com/shay2000/Kestrel-chromium/releases/tag/v1.0.2-chromium-preview.1). The app and checks use source `757a17f779ea6dfe01527500c1189e4cebaedc09`, [complete Mac run 42085793532](https://github.com/shay2000/Kestrel-chromium/actions/runs/42085793532). [Exact DMG and publication provenance](CHROMIUM_1_0_2_RELEASE_2026-11-05.md).

Kestrel retains Chromium's real Chrome toolbar/action controllers inside its existing CEF page window, behind the original SwiftUI header. Its toolbar button, Extensions command menu and optional sidebar shortcuts activate those controllers through public in-process `NSAccessibilityProtocol` objects. No second browser, remote debugging endpoint, system Accessibility grant or navigation to a `default_popup` URL is used by the product. Renderer web areas are excluded from control discovery. Action requests revalidate the selected tab, browser instance, address and request generation after asynchronous menu dismissal.

Settings → Extensions independently controls the macOS command menu, toolbar and shortcuts beside Chats. Sidebar selection persists by Chromium extension ID; legacy settings retain their original menu/import choices. Chromium's pin controls determine toolbar shortcuts. The catalogue reads bounded metadata only from Kestrel's own default profile and approved import directories. Chromium continues to own permission review, installation, site access and action execution.

CEF retains its original native window classes, content views and renderer ownership. The page keeps a 40-point header reservation. Accessibility children are refreshed from the live CEF root instead of keeping an early empty window snapshot. Chromium may relayout its internal toolbar, so native popup positioning uses the existing transient AppKit window and does not depend on overriding that toolbar's layout. It preserves popup size, delegates and lifetime, clamps placement to the owner's screen and stops tracking on dismissal or a context change. A small reviewed CefSwift wrapper reads Chromium's localised UI strings through public CEF resource APIs. Invisible AppKit background views supply actual button geometry without an external accessibility client.

The native restart failure exposed a CefSwift integration bug: selecting `CEF_CTT_NORMAL` creates Chrome's toolbar, but the host must attach `GetChromeToolbar()` to the existing window. The wrapper previously omitted that step. CEF's own `tests/cefclient/browser/views_window.cc::AddControls` demonstrates the required attachment. The fix attaches from CEF's `OnWindowChanged` callback and adds a fixed-height CEF panel to the same page window, with the browser view filling the remaining space; its 40-point row counts toward the existing header inset. It creates no browser or additional native window. Forced renderer accessibility and early argv injection did not fix the missing attachment and were removed. The window census distinguishes controls belonging to Kestrel's own header window from an escaped standalone Chrome toolbar; the real pointer/geometry suite still checks the rendered header and first page row.

The first full regression also caught a transferred-reference bug in the new layout call: CEF consumes a +1 for the view argument to `SetFlexForView`. Each call must receive a temporary retained reference. Keeping the stored panel reference prevents repeated layout and shutdown from using freed memory. A native regression models CEF's argument consumption across 50 updates and verifies the final view release. The UI suite also quits with a genuine popup open. Native layout refreshes only raise the page for its own active document or popup; an independent Settings window must stay above the browser so extension placement choices remain usable.

## Limits

Packaged icons identify shortcuts; dynamic icon artwork and badge mirroring are not established. Compatibility remains bounded to tested extensions and API paths. In particular, Chromium's programmatic `chrome.action.openPopup` checks its browser window feature flags separately from an actual user action; full catalogue-wide Chrome product compatibility is not claimed. Existing initial GET routing does not preserve provisional Chrome tab IDs or virtualise every tabs/windows API.

This work does not change the passkey result. The hosted Mac's virtual Bluetooth controller did not reach a native FIDO QR. Physical phone/QR ceremonies remain unverified, and Apple's Passwords helper still requires Apple's browser identity acceptance. See the existing authentication records.
