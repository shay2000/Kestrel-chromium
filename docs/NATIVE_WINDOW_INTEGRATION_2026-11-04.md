# Native Chromium window integration — 5 November 2026

The user's reports were reproducible: clicking a page made the Kestrel frame inactive, a subsequent toolbar click was consumed, and the page rounded independently below the toolbar. This is a native Swift/AppKit app embedding CEF's Chrome runtime. The extra extension-install window came from Chromium's browser UI inside Kestrel's process; the app does not launch an installed Google Chrome application to install extensions.

## Reproduction and causes

[Baseline run 41871945526](https://github.com/shay2000/Kestrel-chromium/actions/runs/41871945526) operated the **published Preview 2 app**, using real macOS pointer and keyboard events. Page typing worked, but the document lost `AXMain`, the first bookmark click did nothing, and the configured address shortcut failed to move input to the actual search field. The older Store checks used CDP mouse events inside the renderer, so they did not exercise AppKit's activation/first-mouse behaviour.

CEF owns a native child window for each page. Its key/main activation was independent of the SwiftUI document, and the native address field could appear focused while the child retained keyboard input. Applying rounding to that child window also clipped the top of the page below the already-rounded toolbar. SwiftUI cannot clip a separate native window.

The extension path had another ownership gap: auxiliary Chrome UI can inherit an existing app client, as well as use CEF's default client. Both now notify the application. Chromium internally treats the CEF Views host as a popup browser, so its post-install UI can create an ordinary tabbed browser. The app closes that provisional UI and routes eligible initial welcome/options GET pages to Kestrel tabs. This does not implement all Chromium tabs/windows APIs or preserve provisional native tab IDs.

## Changes

- Coordinate the CEF page and its document through `ChromiumWindowAttachment`: keep the document main while its page is key, prepare the clicked native window before first-mouse filtering, and deliver the original event once. Preserve CEF's views and delegates.
- Resolve browser commands and address entry to their owning document. Exclude panels, sheets, modal windows and unrelated windows. Clear address focus when entering a page, including single-page layouts.
- Derive active material appearance per document. Keep inactive applications and other documents inactive.
- Host the existing SwiftUI `BrowserToolbar` inside CEF's own native window, using CefSwift's supported `setContentInsets(top:)` API. The toolbar and webpage now occupy one card window, so native window rounding surrounds the complete card. Reserve the same 40-point toolbar slot in the parent layout and retain the toolbar's controls, font sizes, responsive layout and colours. Remove the earlier unsuccessful attempts to alter AppKit frame/layer clipping.
- When the sidebar is hidden, create native AppKit traffic-light buttons in the header and forward their actions to the owning document. Prevent independent child-window resizing/movement. Route toolbar dragging to the owning document, and keep dropdown hit regions separate from page input. Retain document-main/page-key coordination for the surrounding sidebar and window frame.
- Restrict native drag views to the explicit leading/trailing toolbar padding. A full-background `NSViewRepresentable` wins AppKit hit testing over SwiftUI-drawn buttons: the coordinate trace showed correct button positions, while the drag handler consumed their clicks. Empty margins still drag the owning document; buttons and address entry reach SwiftUI.
- Disable the header hosting view's titlebar safe-area regions: CEF already reserves the toolbar height. Applying the native inset twice shifted the drawn controls below their hit-test region and covered the first webpage rows. Preserve Chromium's accessibility children and expose the SwiftUI toolbar alongside them. Keep the full hosting container's real accessibility frame so SwiftUI computes child-control bounds in the same coordinate space; the contained toolbar supplies its own semantic bounds.
- Chromium's `BridgedContentView.hitTest` returns its Views root before checking AppKit subviews in the reserved header area. `ChromiumNativeOverlays` gives only registered root instances a public `NSView.hitTest` override through an Objective-C runtime subclass. It checks Kestrel's native overlays first and then calls the original CEF implementation. AppKit performs normal gesture dispatch: directly calling `mouseDown`/`mouseUp` does not activate SwiftUI buttons. CEF's root remains the identical window content view, with its renderer hierarchy, native class ancestry and delegates intact. No global method is replaced. Associated overlay references are weak and removed overlays are ignored. A native regression verifies dispatch, fallback, ownership, instance isolation, rebinding and weak lifetime.
- Sample the HTML canvas background before the body background, using an opaque body colour when the root is transparent. This matches WebKit's toolbar on pages such as example.com whose body is transparent over a coloured HTML root. Discard decoration results after a different page starts loading. Native acceptance uses a transparent-body fixture and samples the actual toolbar colour.
- Track the reserved header in `CefBrowserRegistry`. Cursor coordinates and redacted page images use the actual page bounds, excluding native chrome. Geometry regressions cover flipped views, nonzero origins and oversized/negative insets.
- Submit Return and Command-Return using the native editor's current string, protecting against a stale SwiftUI snapshot while keeping the highlighted suggestion route. The test driver sends bounded Unicode events, explicitly clears shortcut modifiers from plain text/pointer events and verifies the complete native field value before Return. It returns to the page after testing the address shortcut, then activates the collapsed address bar with one physical click. Earlier tests never delivered the expected complete destination, so their failed address assertions alone did not establish an application submission race.
- Notify Kestrel for inherited-client auxiliary Chrome UI, with a native lifecycle regression. Preserve explicit DevTools popup handling.
- Fix a separately observed ordinary-network-error crash: `case -200 ... -299` constructed an invalid Swift range inside `reportLoadFailure`. The valid certificate range is `-299 ... -200`. A platform-neutral classifier now covers cancellation, offline/timeout, certificate boundaries and ordinary failures. Native acceptance deliberately refuses a loopback connection and then recovers to a working page.

Renderer sandboxing, native framework/helper packaging and the pinned CefSwift revision remain enabled. This is the existing native Swift/CEF architecture; it is not a newly maintained full Chromium source fork.

## Acceptance

The test uses native pointer and keyboard events for page focus, first-click toolbar actions, address entry and both Store install journeys. It samples the rendered toolbar/page join at both sides and the centre, then verifies the first webpage rows are unobscured. It also checks toolbar dragging and document minimisation/restoration with the sidebar hidden. Test geometry fits the runner's actual display.

The pre-integration tests established that changing content-layer masks, AppKit window style or ancestor clipping did not remove the native window's top corners. Moving the toolbar into the CEF window fixed that clip. [Run 41900908158](https://github.com/shay2000/Kestrel-chromium/actions/runs/41900908158), source `05457d500200356649a72854b5fc62e3e8785b1d`, exposed the additional SwiftUI safe-area offset through real clicks, screenshots and the first-row assertion. [Run 42002524905](https://github.com/shay2000/Kestrel-chromium/actions/runs/42002524905), source `46417b74f93ec54be7e0e902743f111a00847052`, then passed the join and unobscured-first-row assertions, isolating CEF's native hit-test interception as the remaining toolbar failure. The independent lifecycle and both Store install/options/restart journeys passed in those runs, but the workflows failed and supply no release DMG.

[Run 42004560396](https://github.com/shay2000/Kestrel-chromium/actions/runs/42004560396), source `42b7d4569ab0a529403218f150e181b048d076cc`, additionally passed native toolbar dragging after pointer routing, while clicks located through accessibility still failed. The follow-up removes the artificial cropped accessibility frame and disables safe-area regions at the hosting-view boundary. Bounded test-session diagnostics record pointer windows/coordinates and hit-view classes; the driver records control bounds. That failed workflow is not a release origin.

[Run 42006587157](https://github.com/shay2000/Kestrel-chromium/actions/runs/42006587157), source `6ecd7bb0a3b718ba2f66d4064893c5cf7d40f996`, confirmed the bookmark, address and sidebar click coordinates matched their rendered positions. Dragging passed but those controls did not activate, identifying the native background drag view as the remaining interception. The next revision confines it to empty margins. That failed workflow is not a release origin.

The margin-only follow-up still failed SwiftUI button activation, distinguishing direct mouse-method calls from normal AppKit gesture dispatch. An attempted outer content container broke ordinary CEF page opening in [run 42010809179](https://github.com/shay2000/Kestrel-chromium/actions/runs/42010809179), source `56999e46f5baf4a41343cbcd306f943748050b1d`. It was removed: CEF requires its original root to remain the native content view. The per-instance hit-test override retains that invariant. Neither failed run supplies a release DMG.

Accepted [Mac run 42012454676](https://github.com/shay2000/Kestrel-chromium/actions/runs/42012454676), source `f263131f4617eebcecdbda37c8e1987801ec9e87`, passed the entire workflow on macOS 26.6.2 ARM64, Xcode 26.6 / Swift 6.3.3. All **17 native focus/toolbar/network assertions**, the native overlay dispatch/ownership regression, **seven CRX tests** and **nine CEF lifecycle tests** passed. Both Google Translate and Dark Reader installed with native mouse input; all five window-census stages reported **zero extra Chromium toolbars**. Actual extension options and Dark Reader's effect after restart passed. Inspected focus, options, Store and original-WebKit comparison captures. The toolbar aligns with the original and follows its page canvas colour. This is a point visual comparison, not complete split-view/Spaces/tiling or feature-parity certification.
