## Current implementation

- Search-, BrowserOS-, Comet- and Dia-referenced browser shell with a flat toolbar, short domain/search breadcrumbs while the address field is idle, grouped vertical tabs with page favicons, availability-gated Liquid Glass on secondary surfaces and one live `WKWebView` per tab. Kestrel samples only the 30-point visible strips at both page edges locally, refreshing after navigation and scrolling. Those exact strips create restrained, blurred page-edge and assistant-seam reflections; a small colour estimate from the right strip tints the toolbar. Assistant web searches show a softer temporary purple page-edge glow and an explicit progress label. The browser layout compresses below 1,000 points to support half-screen windows. ⌘←/⌘→ target side-by-side tab panes; if the New Tab query is non-empty they search it in the requested pane and keep the existing page opposite, replacing the pane on subsequent uses. With no query they place the selected tab. Both panes keep their live web views, and pane focus drives the shared toolbar and assistant context. Search was cloned to a temporary directory as a read-only reference; its code was not imported.
- SwiftUI/AppKit boundaries are kept in `BrowserView`, `BrowserStore`, `TabStore` and `WebKitConfiguration`.
- ⌘T presents a centred New Tab search overlay on top of the current page; it does not switch to a blank page, and Escape or a second ⌘T dismisses it. Saved bookmarks appear below the idle field, fade away in place while typing, use soft-square favicons with same-site fallback icons, and open in fresh tabs. While typing, local bookmark, open-tab and recent-search matches appear before remote engine suggestions. Up to 50 search terms are retained only in Kestrel's local settings and can be cleared there; external browser history is neither imported nor read. The field uses a denser blurred material, a light gradient and a stronger edge so it stays legible over busy pages. ⌘↩ sends the address-field text to Assistant without replacing a draft already in its composer. The suggestion panel tracks the full field width. Google is the persisted default search engine, with DuckDuckGo and Bing available in Settings; submissions and debounced suggestions follow the selected engine. Suggestions disclose that query text is sent to that provider. A bounded shortcut list supports Tab completion (`maps` then Tab) and explicit bang forms such as `!maps Brooklyn` without opening arbitrary input.
- The Assistant sidebar has a provider picker, compact search composer and a local history menu. Chats can be reopened for follow-up or deleted; the archive keeps bounded user/assistant messages only, never page snapshots, action approvals/results or credentials. A fast on-device intent classifier chooses between an answer, ordinary web search and cursor assistance; deterministic handling overrides a weak answer classification for explicit website actions. The composer's **Web** control is permission, not a command: it decides whether a search is *allowed*, and answering is the router's default. Turning it off cannot make a question into a search, and when it holds back a search the transcript says so. The earlier behaviour — a switch that was on by default and forced every ordinary question through a search, opening a results tab instead of answering — was the bug behind "the assistant just googles instead of telling me". Before cursor operation, Kestrel asks the user; declining takes the ordinary web-search route. The operator model only receives its focused task after opt-in. Explicit image requests are reduced to a subject query and opened in the selected engine's image-search results, rather than searching the instruction verbatim; Kestrel confirms the results tab without claiming to inspect image pixels. Ordinary web-search summaries receive explicit instructions to use the search results already opened. Apple Foundation Models uses greedy sampling and a 12-token ceiling for classification, then route-specific settings: answer temperature 0.7/1,200 tokens, search-summary temperature 0.35/900 tokens and operator temperature 0.15/450 tokens. Assistant guidance asks for appropriately complete answers without padding, and tells the model to qualify unsupported facts instead of guessing; this cannot guarantee local-model accuracy. Apple Foundation Models is an optional local provider, with deterministic routing fallback when unavailable.
- Provider boundaries for Apple On-Device, local Codex and Kilo CLIs, and OpenRouter/Mistral HTTPS adapters. CLI invocation is argv-only. Running an installed CLI from the sandboxed GUI app remains unverified; Kestrel does not open Finder to grant executable access.
- Operator actions are explicit and allow-listed. It proposes at most one action per model response, remains pinned to the initiating tab, waits for navigation to finish before reading fresh bounded/redacted page context, and stops on cancellation, tab change, failure, declined approval, repeated no-progress action or after six actions. For in-page navigation it is instructed to use `find_text` or exact visible links/buttons rather than reload; a repeated refresh on the same URL is stopped before another approval appears. Ordinary web search needs no separate approval. After the user explicitly chooses browser assistance, the safe-browsing preference (on by default) can automatically continue URL navigation, back/forward, reload/stop, find and `search_page` (unique visible search field, same-origin GET form); turn it off to review each navigation. Generic clicks, uncertain actions and mutations remain approval-gated; external MCP actions always use the approval UI. Arbitrary scripts, selectors and shell commands are not accepted. During operation the page shows an animated in-app cursor/target highlight, a progress state and an obvious Stop control; this is visual feedback, not control of the macOS pointer.
- Assistant requests automatically include bounded, visible text from the active page when it can be read. Web searches combine that current-page context with visible search-result text when available. The character budget follows the selected provider/model, using explicit context-window hints when present and conservative provider defaults otherwise. Credential-shaped strings are redacted on a best-effort basis; visible secrets may still be missed, while cookies, storage and hidden form values are not captured.
- The Assistant is available as a right-side browser sidecar and as a full chat page on an empty tab. The page uses a 680-point reading column with a 16-point Markdown body, larger heading/list/code/table roles, a 24-point empty-state title and legible composer text; the sidecar keeps its compact reading scale. Both surfaces share named Kestrel typography roles. Its shortcut is user-configurable in Settings and defaults to ⌘ E. Current-page context is included automatically; Settings explains provider transmission and redaction limits.
- The tab rail and Assistant sidebar can both be resized with accessible drag handles; their widths persist locally and clamp to preserve the page area. Assistant replies render Markdown as separate, spaced blocks: headings, paragraphs, nested bullet and numbered lists, quotes, fenced code, pipe tables and thematic breaks. Tables up to three columns share the width equally; wider ones scroll sideways at a legible column width. Code and tables scroll without a visible scroll bar. Assistant prompts ask models to structure substantive answers without adding headings to simple replies.
- Assistant replies are repaired before they are rendered, and the repairs are deliberately narrow. They split a bold run glued to the next sentence (`**Summary**On 18 September`), put back a space between two sentences that were run together, and never touch fenced code or backtick spans. Two boundaries matter and both are covered by tests: a spacing repair fires only after two lowercase letters, because looking merely for a capital after the dot rewrites `README.MD` as `README. MD` and `https://example.com/a.B` as `.../a. B`; and a bold-run repair must not take a *closing* `**` for an opening one, because doing so breaks `**Mars**, **Earth**` into three lines with stray asterisks on screen. A line of three or more `-`, `*` or `_` is a thematic break, not a paragraph, and a numbered list marker is capped at three digits so a sentence beginning with a year is not drawn as a list item numbered 2026.
- The agent connection is an off-by-default, loopback-only Streamable HTTP MCP endpoint with a Keychain-backed path token. Tab metadata and visible page-text reads have separate opt-ins, and page-changing actions wait for approval in the Kestrel sidebar. Connect Codex adds only the canonical managed block in `~/.codex/config.toml` using a file-specific sandbox exception; the random endpoint token is in that file, which must be treated as sensitive. Settings also retains a manual setup route and local initialise/tool-list test.
- WebKit WebExtension support is availability-gated for macOS 15.4 and later. Kestrel accepts unpacked directories and ZIP archives, not CRX packages, and does not claim full Chromium-extension compatibility. Chromium-origin extensions can work only where their API usage is supported by WebKit; Kestrel does not bundle a Chromium engine.
- Browser Data settings import user-selected Safari `Bookmarks.plist`, Chrome `Bookmarks` JSON, and common bookmarks HTML exports. Only deduplicated HTTP(S) bookmarks are imported; passwords, cookies, browsing history and other browser-profile data are not read or copied. Separately, up to 50 searches entered in Kestrel are held in local settings for address suggestions and can be cleared there.
- Provider picker marks use official provider SVG assets for Codex/OpenAI, Kilo, OpenRouter and Mistral, with their sources and usage notes in `PROVIDER_MARKS.md`; Apple On-Device uses the native Apple system symbol. The image assets are included in both Xcode and the macOS SwiftPM app bundle.
- Model identifiers are chosen rather than typed. `ProviderModelCatalogue` reads OpenRouter's and Mistral's published model lists over HTTPS and Codex's own `codex debug models` output; `ProviderModelPicker` presents them in the Assistant popover and in Settings, with a search field, a loading/error line, preserved selection and a manual-entry fallback. OpenRouter's free and automatic routers are built in and listed first so a user without credit has a working choice immediately. Loading OpenRouter's list deliberately does not read the Keychain — a Keychain read can raise a system password prompt, and merely browsing a model list must not — and `FailingSecretProvider` in `Secrets.swift` is the test double that proves it stays that way.
- Codex CLI output is parsed rather than displayed raw. `CodexEventParser` reads the JSONL event stream from `codex exec --json` and returns only assistant prose, surfacing usage-limit, authentication, sandbox and turn-failure events as their own messages. The default argument template is `exec --json --skip-git-repo-check --sandbox read-only --ephemeral --color never -m {model} {prompt}`; `AISettings.migrateLegacyDefaults()` replaces the previously shipped `exec {prompt}` template, which could never work because `codex exec` refuses to run outside a trusted directory. An empty model selection drops the `-m` flag and its value together rather than passing a dangling flag.
- The **Exa** web-search connector is opt-in and off by default. With a key in Settings, an Assistant web search goes to Exa's search API over one HTTPS call instead of driving a search-results page, and each result is preserved as its own labelled, bounded citation through `PageContextBuilder.combining`. `ExaRedirectGuard` strips the API key on cross-host redirects and refuses HTTP downgrades. Without a key the Assistant keeps the existing search-page path and reports which key is missing.
- The new tab page is a Dia-inspired surface rather than a blank pane. Launching Kestrel opens it instead of a website the user did not ask for. It shows a labelled **Search** field over a translucent material that lets the desktop read through, with `NewTabAttachment` providing **Upload** (a text file, read locally, bounded per item) and **Connect tab** (another open tab's visible text, read through `TabStore.captureTabSnapshot`, which deliberately bypasses the active-tab guard that browser *actions* use). Attachments appear as removable chips and are bounded both individually and in total; the prompt budget is charged for headings and separators as well as bodies. A question carrying attachments is routed to Assistant rather than to a search-results page. Clicking the page behind the overlay dismisses it, and the pane's outline is now a dark-mode-only hairline so the surface reads as continuous rather than framed.
- Settings, bookmark format parsing, Keychain-backed provider secrets, provider endpoint validation, URL normalisation and tab-selection validation are covered by platform-neutral tests.

## Native passwords and passkeys

Kestrel deliberately relies on the system/WebKit path rather than creating its own credential store:

- `WKWebView` is retained with the default website data store and JavaScript enabled, so websites can use their normal HTML Password AutoFill and Web Authentication flows.
- Apple’s documented WebKit behaviour handles Web Authentication for web content. Kestrel must never extract, display or send website passwords, cookies or passkey private material to the assistant.
- Site-specific WebAuthn in a `WKWebView` can use a `webcredentials` associated domain when Kestrel owns or is explicitly associated with that site.
- A general-purpose browser needs Apple-managed browser capabilities for arbitrary relying parties and unrestricted browser Password AutoFill:
  - `com.apple.developer.web-browser`
  - `com.apple.developer.web-browser.public-key-credential`
- The normal local target uses `KestrelWebKit/Entitlements/KestrelWebKit.entitlements` (sandbox, read-only access to user-selected import files, network client and network server for the opt-in loopback MCP listener). The separate `KestrelWebKit/Entitlements/KestrelWebKit.browser-passkeys.entitlements` file is an approval-only template and must not be enabled before Apple grants the capabilities and the provisioning profile includes them.
- Settings checks the running app's signed entitlements and shows the Authentication Services access state. The OS permission request is user-triggered and remains disabled unless both managed capabilities are actually signed into the app.
- The app declares HTTP and HTTPS URL schemes in `Info.plist` so it is structurally ready for Apple’s browser-capability review. That declaration alone does not grant the managed entitlements.

## Sandboxed builds and the preferences trap

Kestrel is a sandboxed app. That makes the signature load-bearing for the user's data, not just for Gatekeeper:

- A sandboxed Kestrel reads and writes its preferences inside `~/Library/Containers/com.shayprasad.Kestrel/`. An **unsandboxed** Kestrel reads `~/Library/Preferences/com.shayprasad.Kestrel.plist` instead. These are different files.
- So an app that loses its sandbox entitlement does not merely lose a permission: the user's bookmarks, recent searches and saved chats all appear to have been deleted, and every new one is written to the wrong file until the next good build. Nothing is actually lost — the container is untouched — but it looks exactly like data loss, and it is easy to misdiagnose as a code bug.
- The entitlement is applied by `codesign` at packaging time. If that step is interrupted — killed, out of disk, a tool that exits 0 anyway — the bundle keeps the linker's bare signature on its executable, which carries no entitlements. `codesign --verify` does not catch it, because the bundle is not *mis*-signed; it is signed with the wrong entitlements.
- `build.sh` therefore reads the entitlements back after signing and fails loudly if `com.apple.security.app-sandbox` is missing. Keep that check. When packaging by hand, run the same read-back before launching the result:

```bash
codesign -d --entitlements :- build/Kestrel.app | plutil -p - | grep app-sandbox
```

- Diagnosing it after the fact: `codesign -dvvv <app>` showing `Sealed Resources=none` and an identifier like `Kestrel-<uuid>` rather than `com.shayprasad.Kestrel` means the bundle signature never landed and the executable's own signature is what you are looking at.
- The workspace attaches `com.apple.FinderInfo` and `com.apple.fileprovider.fpfs#P` to bundles under the repository, and `codesign` refuses to sign a bundle carrying them. Package to a directory outside the workspace (for example `/private/tmp/kestrel-app`) and copy the finished bundle into `build/` with `ditto`. Do not delete and re-sign in place under `build/`.
- Do not pipe the packaging command through `tail` or similar: the pipeline's exit status hides the script's, and the missing `built: …` line is the signal that it did not finish.

## New tab page and address dropdown

The most recent UI pass changed the new tab page and the address field's dropdown. What it did, and what to watch for when changing it again:

- **Attachment policy lives in one place.** `NewTabAttachment.swift` owns the extension lists, the size and character budgets, the prompt that joins a question to its material, and the open panel's allow-list. `NewTabAttachmentBuilder.selectableContentTypes()` is built from the same policy the reader applies, so the picker cannot offer a file Kestrel would then refuse. Add a format to `readableTextExtensions`, `passThroughTypes` or `OfficeDocumentText.supportedExtensions` and the picker follows automatically — do not add a second list.
- **Word, Excel and PowerPoint are read locally.** `OfficeDocumentText.swift` inflates the Office ZIP container using `Compression` and pulls the text out of `word/document.xml`, `xl/sharedStrings.xml` and the `ppt/slides` parts. Sizes come from the ZIP central directory, because a streamed archive leaves the local header sizes at zero. This means Office attachments work with every provider, not only a hosted one. It is a text extractor, not a document renderer: formatting, images, charts and comments are not read.
- **The dropdown's row count is derived, not fixed.** `SuggestionPanelLayout.swift` turns a screen height into a row budget and shares it between the bookmarks, recent-searches, tab and remote-suggestion sections one row at a time. Keep it SwiftUI-free and keep the tests green: the invariant that matters is that a panel sized from the budget stays on screen whenever the display has room for the minimum row count. `fixedChrome` is deliberately an upper bound on the panel's non-row content, so if you add a section or a footer row, raise it. The tab section is labelled **Tabs**, not "Open tabs", because it lists Kestrel's own tabs rather than anything the page opened.
- **The dropdown must draw above its later siblings.** `AddressEntry`'s panel is an overlay on the field, and the new tab page puts a divider, the action row and the bookmark shelf after the field in the same stack. Without the `zIndex` lifts in `FloatingNewTabSearch`, those siblings paint over the panel's first rows. If you add another element below the field on that page, give it a lower `zIndex` than the block.
- **⌘T is derived from the tab, not from a flag.** `TabStore.selectedTabHasNoPage` decides whether ⌘T presents the search page or toggles the overlay, and the view keys the field on the same property. Keying either one on `isNewTabSearchPresented` alone is what produced an empty pane with no bar; `TabModelTests` covers the regression.
- **Search history keeps the query, not the bang.** `AppSettings.recordSearch` normalises through `SearchShortcut.strippingLeadingShortcut`, so `!maps eiffel tower` is stored as `eiffel tower`. Only the bang form is stripped — a bare `maps` is an ordinary search term, and an unknown `!token` is left alone.

Verified by hand on this Mac with a signed local build: the bang routes to Google Maps, the history entry reads `eiffel tower`, the dropdown draws over the action row and shelf with no overlap, it shows five rows for the floating field and nine for the toolbar field on a 1512×982 display, and the tab section is labelled `Tabs`. The screen-derived budget and the section allocator are covered by `SuggestionPanelLayoutTests`, and the history and bang rules by `SettingsAndProviderTests`.

`swift build`, `swift test` and the SwiftPM app bundle are the working path on this machine. The Xcode target previously failed at `SwiftCompile` with `external macro implementation type 'SwiftUIMacros.StateMacro' could not be found for macro 'State()'` / `swift-plugin-server produced malformed response`, on pre-existing `@State` declarations in `ContentView.swift`, `SettingsView.swift` and `AISidebar.swift`. **That is now solved, and it was never a source problem.** The compiler runs macro plugin servers inside its own `sandbox-exec` wrapper, and the outer sandbox denies `sandbox_apply` — the same root cause as SwiftPM's manifest sandbox. The give-away is the first line of the failure output, `sandbox-exec: sandbox_apply: Operation not permitted`, which is easy to miss above the macro errors. The fix is the compiler's own switch:

## Chrome polish: selection, the new tab page's real painter, and the bang

- **An empty `WKWebView` is not empty.** It paints its own background, which is
  white in the light appearance. `browserPage` always rendered `BrowserView`, so
  on a tab with no page WebKit painted the page and `pageSurfaceBackground` was
  never visible — the new tab page measured `#1E1E1E`
  (`NSColor.windowBackgroundColor` in dark mode) rather than the `#212121` the
  code asked for. That is why the page looked light in dark mode and flashed
  white when the window lost focus. `BrowserView` now takes `isHidden`, and
  `browserPage` hides the hosted view while the tab has no page. It stays in the
  hierarchy, so the tab still loads and keeps its scroll position and form state.
  With the surface visible the page measures `#212121` — the same charcoal as the
  rail, from the shared `kestrelDarkChrome` constant, so the two cannot drift
  apart again. Light mode still uses `.ultraThinMaterial`, matching the light-mode
  rail.
- **Selected tabs are a soft-UI tile, not an accent outline.** `TabSelectionSurface`
  gives both the pinned-tab tiles and the regular rows a near-white gradient fill,
  two stacked drop shadows and a top-lit hairline. Its unselected state is
  parameterised (`restingFill` / `restingBorder`): pinned tiles rest on a faint
  tint, list rows on nothing. The fill is near-white in *both* colour schemes, so
  nothing drawn on a selected tile may use `.primary` / `.secondary` — those flip
  to white in dark mode. Hence `TabRowView.titleColor` / `detailColor` /
  `closeColor`, and a neutral `PageFaviconView` chip.
- **Scroll-edge fades appear only where content is hidden.** `FadingHorizontalScroll`
  wraps the bookmark shelf and the composer's action row and derives its mask from
  the scrolled content's frame and the viewport width. Both ends used to fade
  unconditionally, which dimmed the first bookmark chip at rest.
- **The new tab page's `onSubmit` used to discard the prepared query.** It was
  wired `{ _ in submit() }`, and `submit()` re-read the raw `query` binding, so a
  shortcut committed with Tab never reached the destination URL: the badge said
  "Google Maps" and the search went to Google. `submit(_ prepared:)` now takes the
  field's prepared query. The toolbar field was already correct.
- **Tab removes the "Chat" row.** `routeRowCount` is 2 normally and 1 while a
  shortcut is committed, and the panel, `chooseSuggestion` and the arrow-key bound
  all derive their offsets from it instead of a literal `2`. The route row names
  the shortcut, and emptying the field clears it so a mistaken Tab is reversible.
- **The page-context card is pinned under the sidebar header.** `AIChatStore`
  clears `lastPageContext` at the start of every request and only refills it when
  the re-read returns something, so the card — which lived above the latest user
  message — vanished on every follow-up. It is now a fixed band backed by
  `pinnedPageContext`, re-seeded when `chat.items.first?.id` changes.

## The top bar takes the menu bar's colour

Requested as: *"make the top bar match the top of the screen colour wise like how
dia does it"*. Four separate faults were stacked on top of each other, and each
one hid the next.

1. **The page pane was the whole column, not the page.** In `ContentView` the
   `ZStack` holding `browserPage` was followed by `.padding(4)`, `.frame(...)`,
   `.background { pageSurfaceBackground }`, and then a closing brace — and the
   `.frame` / `.background(windowBackgroundColor)` / `.clipShape(browserPaneShape)`
   / `.overlay { browserPaneBorder }` chain *after* that brace sat on the
   enclosing `VStack`, not on the page. So the pane's flat `#323232` fill and its
   17-point rounded corners also covered the toolbar, which was drawn on top of a
   grey card. Proven by temporarily colouring that background red: the toolbar
   band turned red. The four modifiers now live on the page's `ZStack`, and the
   toolbar sits over the window backdrop.

2. **The window's background was never cleared.** `WindowChromeProbe` did
   `if window.isOpaque { window.isOpaque = false; window.backgroundColor = .clear }`.
   SwiftUI hands over a `.hiddenTitleBar` window that is *already* non-opaque, so
   the branch never ran and `backgroundColor` kept its default. The two
   assignments are now unconditional.

3. **`NSVisualEffectView` inside SwiftUI does not blend behind the window.**
   Handed to `.background`, the same effect view renders as an opaque slab and
   never samples the desktop: measured over one wallpaper the menu bar read
   `#161529 … #1F2137` across the screen while a `.background`-hosted blur read a
   flat `#232326` everywhere. It has to be a direct descendant of the window's
   content view.

4. **…and the content view is SwiftUI's own.** `contentView.addSubview(_:positioned:.below, relativeTo: nil)`
   put the blur *above* the whole interface — the window rendered as nothing but
   blurred wallpaper. SwiftUI's content view draws its own hierarchy rather than
   holding it as subviews, so a subview added to it lands on top. The backdrop
   goes in `contentView.superview` (the window frame), positioned below the
   content view.

What is left is `WindowBackdrop.make()` — a behind-window `NSVisualEffectView`,
material `.headerView` — installed by `WindowChromeProbe`. The rail's title-bar
row is left bare (`TabStripView` splits its 44-point spacer out of `railBody`),
so one backdrop runs the full width of the window: rail row and toolbar are now
the same surface, the way a macOS window's sidebar begins below its title bar.

Measured with a signed build: the strip tracks the wallpaper (it lifts to
`#1F2128` where the menu bar lifts to `#1C2038`) and sits about 13 levels lighter
than the menu bar. No public material closes that gap — a throwaway probe window
under the menu bar, comparing `.menu`, `.headerView`, `.titlebar`, `.sidebar`,
`.underWindowBackground`, `.hudWindow`, `.contentBackground` and `.popover`
against a control block showing the bare desktop, found **every** material lands
8–25 levels *lighter* than the menu bar over this wallpaper, because the menu bar
carries a dark tint of its own. `.contentBackground` is the darkest and `.menu`
the lightest; `.headerView` is the one that matches the surface semantically.
Adding a fixed dark overlay would close the gap but is wallpaper-dependent, so it
was left out.
